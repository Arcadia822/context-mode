# ADR-0007: MCP spec 2026-07-28, with 2025-xx clients still served

- Status: Accepted (2026-10-14, user asked for the latest MCP spec)
- Related: ADR-0004 (instructions), ADR-0006 (alwaysLoad), TECH-SPEC §3

## Context

**Latest spec: 2026-07-28** (versions in the spec repo: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28, draft). Changes that affect context-mode, quoted from `docs/specification/2026-07-28/changelog.mdx`:

| Change | Effect on context-mode |
|---|---|
| "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta`" | The server must not keep state per connection. Client info is read from each request's `_meta` |
| "Add `server/discover`: servers MUST implement this RPC" | New RPC. `DiscoverResult` carries `supportedVersions`, capabilities, `serverInfo` and `instructions` (schema.ts:678-696) |
| "Remove `ping`, `logging/setLevel` …" | No logging feature. Logs go to stderr |
| "All results now carry a required `resultType` field" | Every result gets `resultType: "complete"` |
| "`ttlMs` and `cacheScope` on results returned by `tools/list` …" (`CacheableResult`) | `tools/list` and `server/discover` must return them |
| "Servers SHOULD return tools from `tools/list` in a deterministic order" | Fixed tool order (also helps prompt caching, PR9) |
| `inputSchema` may use any JSON Schema 2020-12 keyword | Schemas may use 2020-12 |
| Deprecated: Roots, Sampling, Logging (SEP-2577) | Already decided: no roots (README §5) |

**What the clients actually send today.** Live probe, 2026-10-14. A stub server logged every request.

| Client | First request | protocolVersion |
|---|---|---|
| Claude Code 2.1.283 | `initialize` | `2025-11-25` |
| Codex CLI 0.156.1 | `initialize` | `2025-06-18` |

Neither client called `server/discover`.

Client SDKs in source:
- Gemini CLI: `@modelcontextprotocol/sdk` 1.23.0
- Qwen Code: `client` 2.0.0 and `sdk` 1.26/^1.30
- OpenCode: `client` 2.0.0
- Codex: `rmcp` 3.5.1

**Official TypeScript SDK:** `@modelcontextprotocol/server` v2.3.1 (2026-10-05) "implementing the 2026-07-28 MCP spec". Its `SUPPORTED_PROTOCOL_VERSIONS` also lists 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05 (`packages/core/src/constants.ts:1-3`). v1 of context-mode uses `@modelcontextprotocol/sdk` ^1.26.0.

## Decision

1. **The server implements 2026-07-28** with `@modelcontextprotocol/server` v2.x, bundled (no npm at runtime). Stdio transport only.
2. **It also serves 2025-03-26 … 2025-11-25 clients** through the same SDK's version negotiation. This is the protocol version negotiation the spec defines, not a fallback in our code: one server and one tool set, answered in the version the client asks for.
3. **Instructions are delivered in both places, with the same bytes:**
   - `InitializeResult.instructions` for 2025-xx clients
   - `DiscoverResult.instructions` for 2026-07-28 clients
4. **Stateless server:**
   - No per-connection state.
   - The agent and the session are identified from request `_meta` and hook payloads, never from the connection.
   - This also fits the single `context.db` (ADR-0002).
5. **Results:**
   - `resultType: "complete"` on every result.
   - `tools/list` returns the 9 tools in a fixed order, with `ttlMs` and `cacheScope: "public"` (the list does not depend on the user).
6. **Not used:** roots, sampling, logging, resources subscriptions, tasks, elicitation, MRTR.
   - Errors go back as tool results with `isError: true` and a one-line fix.
   - Logs go to stderr.

## Tests

GP1 and GP2 run each case twice:
- an `initialize` client at 2025-06-18 and at 2025-11-25
- a stateless 2026-07-28 client that calls `server/discover` first

Both runs must produce byte-identical instructions and tool lists.

GP-LIVE runs the real agents and logs the protocol version each one negotiated, so a version change in an agent shows up.

## Consequences

- Current agents keep working, because they still send `initialize`.
- Agents that move to 2026-07-28 are already supported.
- context-mode depends on the SDK's version negotiation. An SDK upgrade is gated by GP1/GP2.
